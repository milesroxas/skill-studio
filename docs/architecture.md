# Architecture

One table of operations serves the desktop app and the web server. [`src/application/api/contract.ts`](../src/application/api/contract.ts) names each operation with its input and output, and `operations.ts` beside it checks the input and runs it. The desktop app calls the table over IPC and `st serve` exposes it as `POST /api/<name>`, so an operation added once reaches both. The CLI has its own fixed commands, which call the same application functions.

## Layers

```
src/
  domain/          pure: schemas, read models, scoring, stats, text. No I/O
  judges/          the judge packs (generic, writing, code, workflow, design), one folder each, and the Jev client
    rule/            the judge behind the editor's selection popout; not a pack
    shared/          what the packs share: Jev questions, scoring helpers, asking for a check command to be run
  application/     use cases (generate, grade, jobs, the assistant) and the operations table
  infrastructure/  files on disk, the environment
    engines/         the agent CLIs: claude, cursor
    ai/              the assistant's providers
  interfaces/
    host.ts        the checkout's paths for the CLI and `st serve`: `.env` and `out/renderer`
    lifecycle.ts   what every host does about agents: end a crashed copy's, record its own, end them on a signal
    renderer-files.ts  the built renderer's file for a request path, for the `studio://` scheme and `st serve` alike
    electron/      main process, preload bridge, backend utility process
    http/          `st serve`: the table over HTTP, the request guard, Tailscale
    cli/           the `st` command
  renderer/        the React app; reaches the table through a transport (IPC or HTTP)
    components/ui/   shadcn/ui sources (Radix + Tailwind v4), owned by the repo
    components/      the app's composites built on them
    editor/          CodeMirror: the Markdown language, the theme, the live preview
    lib/             `cn`, the class-name helper
    screens/         one file per screen
```

Imports point inward only, and `pnpm fallow` fails on one that does not (`boundaries` in `.fallowrc.json`):

| Layer | May import |
| --- | --- |
| `domain` | nothing |
| `judges` | `domain` |
| `infrastructure` | `domain`, `judges` |
| `application` | `domain`, `judges`, `infrastructure` |
| `interfaces` | all of the above |
| `renderer` | `domain`, `judges`, and types from `application` |

## The desktop app

- Operations run in a backend utility process, not the main process, so the window never waits on a file read, a hash or an agent.
- An app opened from the Finder or the Dock gets the system's bare PATH (`/usr/bin:/bin:/usr/sbin:/sbin`), where no CLI in the home folder or Homebrew is found. The main process starts the backend with the installers' folders added (`~/.local/bin`, each nvm Node's `bin` newest first, `~/.volta/bin`, `~/.bun/bin`, `~/.npm-global/bin`, `/opt/homebrew/bin`, `/usr/local/bin`), then reads the login shell's PATH (`$SHELL -ilc`, five seconds at most, taken as soon as it is printed even if a startup file left something holding the output open) and hands it to the backend with `setEnv` (`src/infrastructure/path.ts`). A shell that does not answer in time is asked once more ten seconds later, with fifteen to answer. Home is `os.homedir()`, which reads `HOME` as the Claude Code installer does.
- A CLI is found by searching the PATH (`resolveCommand` in `src/infrastructure/exec.ts`), with `PATHEXT` on Windows, and started by its full path; `PATH` and `PATHEXT` are read whatever the case of their names there. A `.cmd` or `.bat` runs through cmd.exe, with every argument quoted and each character cmd.exe acts on escaped with a caret, twice, since the script reads its arguments once more (`cmdLine`); an argument with a line break cannot cross a cmd.exe line, so the run is refused with a line saying so. On POSIX each is started as its own process group, and ending it ends the group.
- One function starts every process the backend runs, `exec` in `src/infrastructure/exec.ts`: the agents, the assistant's CLIs, and the code pack's check command, which is shell command lines. A judge pack starts nothing itself: grading puts a runner on the judge context (`JudgeContext.run`, a `CommandRunner` from `commandRunner(signal)`), so a check command is ended as a group at its timeout, when its job is stopped and when the app quits. Stopped before it starts or while it runs, the runner rejects with "Stopped.", so a command cut short is never read as the check's answer. Everything `exec` starts gets `agentEnv()` unless it is handed another environment. Output is decoded as a stream, and kept within bounds: stdout from its start up to 16 MB, or its last 64 KB when the lines are handed on as they arrive, and the last 64 KB of stderr. A process asked to end gets five seconds, then is ended for good, and the run settles a quarter of a second later whether or not its output has closed. A process that exits while something it started still holds its output open (a server put in the background with `&`) settles once that output has been quiet for half a second, with the process's own exit code; for a shell line on POSIX, and for a run that was being stopped, what is left of its process group is ended then.
- Quitting holds `will-quit` until the backend has ended the processes it started (`stopAll`), three seconds at most, then quits for real; an update's restart quits the same way. From the moment `stopAll` is called `exec` starts nothing more and rejects with "Stopping.", so a job between two agents cannot start the next. The backend records the agents it starts in `~/.skill-studio/agents.json` (`src/infrastructure/children.ts`), each with the pid and start time of the backend that owns it, since every running copy of the app shares the file. A backend that starts ends the agents whose owner is gone (`endOrphans`), after checking each pid is still that command, started when the record says, and leaves the records of a copy that is still running. An entry that is not a whole-number pid above 1 with one of the agent commands (`claude`, `cursor-agent`, `codex`) is ignored. Checking each record runs `ps`, so the file is read again just before it is written and only the records found orphaned are taken out: a record another copy wrote meanwhile stays. A record that cannot be written is warned of once and never stops a run, nor the start of the backend or `st`.
- JSON the app writes (`run.json`, `report.json`, `reviews.json`, versions, drafts, settings) goes to a temporary file beside the target and then takes its name (`writeJson`), so a crash leaves the old file whole. The text files it writes go the same way (`writeText`): `SKILL.md`, a reference, and a case's `prompt.md`, `case.yaml` and checks. A file that does not parse throws an error naming it (`readJson`); the lists of runs, versions, cases and lock files skip a bad one with a warning rather than fail whole.
- A path from a request is checked twice (`src/infrastructure/fs.ts`). `assertSafePath` takes any name a folder can hold, spaces and other alphabets included, and refuses an empty part, a hidden name, `..`, a backslash, a control character and any of `< > : " | ? *`, so a skill opens on every system; on Windows it also refuses a device name such as `con` or `nul.md` and a name ending in a dot or a space. `assertInside` then resolves every link on the way and refuses a path that ends outside the skill, or at a link to nothing; a file not there yet is judged by the nearest folder that is. Saving, deleting and restoring a skill file, saving and deleting a case, reading a picture and serving a sample's file all go through it. `readTree` passes over a link that leaves its folder, and the scan of a sample's `outputs/` follows no link at all, since the agent wrote that folder.
- Stopping everything is one function, `shutdown` in `src/application/shutdown.ts`: it stops every job (`stopAllJobs`) and every assistant reply (`stopAllRuns`), then ends the processes still running (`stopAll`). Quitting the app calls it, and so does the CLI on SIGINT (Ctrl-C), SIGTERM and SIGHUP (the terminal closing), through `agentLifecycle` in `src/interfaces/lifecycle.ts`, before it exits with 130, 143 or 129. `st serve` also keeps running through an error nothing caught (`keepRunning`), as the desktop backend does: the error is logged and every job goes on.
- Job changes and assistant replies are pushed to the window as they happen. A browser polls instead.
- A job (`src/application/jobs.ts`) has an abort controller, kept out of the job the window reads. `jobs.stop` fires it: generation stops taking samples and ends the agents in flight (the signal reaches `exec` through `EngineRequest.signal`), grading stops before its next sample, keeps no answer from the sample the stop came in, and writes no report, and the job ends as stopped, with "Stopped." in its log. A job names what it works on, the skill path or the run, so a second run of the same skill or a second grading of the same run is refused while the first runs; the grading a run job does on the run it made counts as a grading of that run. A run job lists the runs it is writing (`Job.writing`, set once `generateRun` names each run): only those are refused a grading or a delete, so a run cut off earlier can be graded or deleted while another run of the skill is written. A run being graded is refused a delete too. A grading with no output to grade (every one stopped before it was written) writes no report, says so in its log and ends as failed. The list the window reads holds every running job and the newest 12 finished ones (`listJobs`), and "is anything running" asks every job, listed or not (`anyRunning`): deleting a version and restarting the walkthrough wait on it. The last 50 finished jobs are kept. A job's log keeps its first 100 lines and its latest, 500 in all.
- A run is made from copies taken as it starts (`src/application/generate.ts`): the skill as an agent's copy holds it goes to the run's `_skill/`: without `evals/`, hidden files, `node_modules`, `venv` and `__pycache__` folders at any depth, or links that leave the skill, which is also exactly what the version's hash covers and each case's input files to `_inputs/` (made even when no case has a file), and every sample is built from those. Grading reads a case's pictures from `_inputs/` too, as the agent got them, each only when it is a file inside that folder; a run with no `_inputs/` is from before runs kept one, and its pictures are read from the case as it is now. Saving, restoring or editing the skill while the run goes on changes nothing the run reads. When the run's folder can no longer be written to, every worker stops and the agents in flight are ended. A case's `timeout_seconds` is held to six hours.
- The renderer reaches the main process through one preload bridge (`window.studio`), with one function per message.
- The packaged app loads its pages from `studio://app/`, a sample's files from `artifact://sample/<skill>/<run>/<sample>/<file>` and a picture from `artifact://image?...`. A sample's file is named by its path (`src/domain/artifact-address.ts`), so a page an agent wrote finds the files beside it by their relative names, as it would on disk. `?stage=1` asks for a page as Results' stage shows it, with a short script that lets two pages scroll together and passes A and B up (`withStageBridge` in `src/application/api/artifact-page.ts`).
- Grading draws a page for Jev to look at (the generic and design packs both do), and only the main process has a browser to draw with. The backend posts `render` with the page and a size (`PageRenderer` in `src/domain/artifact-address.ts`); the main process loads it in an offscreen window (`src/interfaces/electron/main/render.ts`), one page at a time, and answers `rendered` with a PNG of exactly that size. `gradeRun` draws a page in a window the case's size, or 1280 by 960, and at 390 by 1200 too for a case that asks for a phone, keeps the PNGs in the sample's `renders/` folder named by their size, and draws again only when the page is newer. The CLI and `st serve` have no renderer, so there a page is judged by its HTML and any screenshot the agent left.
- A key in the environment at launch wins over a stored one. A stored Anthropic or OpenAI key reaches the backend under a name of the app's own (`SKILL_STUDIO_ANTHROPIC_API_KEY`, `SKILL_STUDIO_OPENAI_API_KEY`), so an agent the app starts does not bill a key stored for the assistant.

[SECURITY.md](../SECURITY.md) covers the hardening, and [cli.md](cli.md#the-web-server) the web server.

## The loop in the renderer

A skill has three screens (`SKILL_PLACES` in `src/renderer/places.ts`), one per step of the loop that is a place:

- **Skill** (`screens/Editor.tsx`) edits `SKILL.md` and `references/`, and lists the versions. A version opens in the main column (`components/VersionDetail.tsx`) with its changes and Restore.
- **Cases** (`screens/Cases.tsx`) edits the cases a run is made of. A case needs a prompt only.
- **Results** (`screens/Results.tsx`) lists the cases a run answered and compares two outputs of the one picked (`components/Comparison.tsx`). "All cases" is every run at once (`components/ResultsSummary.tsx`), with Graded as folded at its foot (`components/GradedAs.tsx`).

Running is a button in the top bar, not a screen (`components/Run.tsx`): it calls `skill.generate`, which keeps the files as the next version when they changed since the last run.

`src/domain/pairs.ts` chooses the pair a case opens with: the latest version beside the one before it, by the same writer where it can.

What a reader says is a **correction** to one verdict (`skill.correct`), kept in `evals/reviews.json` and written from Results. Every pack's scorer reports the facts it counted (`Verdict` in `src/domain/pack.ts`) and takes the reader's corrections, so a score follows a correction with no new call to Jev. [grading.md](grading.md#verdicts) has the details.

A retired screen's address opens the screen its work moved to (`MOVED_SCREENS` in `src/domain/preferences.ts`). A name the app has no screen for opens home (`screenFor` in `src/renderer/next-step.ts`).

The shell (`App.tsx`) holds what every screen reads and hands it to them as one object (`Ctx` in `src/renderer/ctx.ts`), built again only when something in it changes:

- **The open skill** (`useSkillState` in `src/renderer/skill-state.ts`): its state, its scoring (`bench.json` over the defaults) and its files as saved. Every call addresses the skill open when it is made, so a reply that lands after another skill was opened is dropped. Reads of the one skill can land out of order: a reply is dropped only once a newer one has landed, and an awaited `reload` resolves once every read asked for after it has landed too (`createReads` in `src/renderer/reads.ts`). The saved files are read once (`ctx.files`) for the Editor and the side panel, and a save updates the copy at once (`took`), so the text in view never steps back to the file from before the save.
- **The jobs** (`useJobs` in `src/renderer/use-jobs.ts`): pushed by the desktop app and polled in a browser. The skill is read again when a job ends, and at most every two seconds while a run of it writes outputs.
- **The drafts** (`useDrafts` in `src/renderer/drafts.ts`): unsaved files and cases, stored on disk half a second after the last keystroke. A save clears its draft unless more was typed while it was written; that text stays, as a draft begun on what was saved (`src/renderer/draft-edits.ts`). A save that ends after another skill was opened clears the draft in that skill's stored drafts. A read of the stored drafts that fails is tried three more times before an edit may be stored over them, and a read waits for any write under way. A draft of a case the skill no longer has is dropped. A draft that says what the disk says is no unsaved work: an unsaved file is one whose draft differs from the file on disk (`unsavedFiles` in `src/renderer/changes.ts`), and an unsaved case one whose draft differs from the case (`unsavedCases` in `src/renderer/draft-edits.ts`). In a browser the drafts stored as the tab closes go as a request the browser keeps alive, when the body is at most 60,000 bytes; a write already under way as the tab hides is sent again that way.
- **When a case draft began** (`caseBases` in the drafts): the case's `savedAt` as the draft began, stored with the drafts, so a draft read back after a restart still knows. A save sends it, and the host refuses the save when the case on disk is newer. Cases says the case changed on disk as soon as a read shows it newer, as the Editor does for a file (`FileDraft.previous`). A draft stored before bases were kept is taken as begun on the case as it is when first shown.
- **The next step** the top bar offers (`nextStep` in `src/renderer/next-step.ts`): add a case, run, read the results of a run that finished since Results was last open, or the walkthrough's own step. When Results was last open is kept per skill in the window's storage (`src/renderer/results-seen.ts`), so a cleared store asks once more.

A store kept outside React (the route, the preferences, the updates, the assistant) is a `createStore` or a `createEmitter` from `src/renderer/store.ts`. An awaited step behind a button is `useAction` in `src/renderer/hooks.ts`: busy while it runs, with a failure on the status line. `useFetch` there never shows what it read for one set of `deps` under another; a value that changes under the same `deps` is read again with its `reload`, which keeps the last value in view. A step that ends after another skill was opened leaves that skill alone. Opening another skill clears the notice on the status line before the skill opens, so a step that reports once its skill is open, such as making a skill, reports after the open.

Back and Forward return to the skill a place was seen in. Until that skill is open the shell keeps the place the reader is on in view, so no screen shows one skill's place with another's data.

## Engines

An engine runs one agent CLI in a sample directory (`src/infrastructure/engines/`).

- **claude**: `claude -p --output-format stream-json --verbose --no-session-persistence --strict-mcp-config --setting-sources project --permission-mode acceptEdits`, with `--allowedTools` set from the case's `allowed_tools` (by default Read, Write, Edit, Glob, Grep and Bash). Only the sample directory's own settings load, so the machine's skills, `CLAUDE.md` and MCP servers stay out of the run. The environment is the backend's less three things (`agentEnv` in `src/infrastructure/env.ts`): variables starting with `CLAUDECODE`, so a run works from inside a Claude Code session, and `TYPESAFE_API_KEY` and every `SKILL_STUDIO_*` variable, so an agent with Bash never sees the app's keys. The assistant's CLIs get the same environment. Models offered: sonnet, opus, haiku, fable, and default (the CLI's own, with no `--model` flag). Any other name the CLI may know is passed on too, its own aliases (`opusplan`), full ids (`claude-…[1m]`) and Bedrock and Vertex ids included, as long as it is one argument and nothing else: 1 to 120 letters, digits and `. _ - : @ [ ] /`, starting with a letter or a digit. The CLI says itself when it has no such model. Efforts: low to max. A model or effort outside those is refused before anything starts, as it is for every engine (`chosen` in `engines/stream.ts`).
- **cursor**: `cursor-agent -p --output-format stream-json --force --trust`. It needs `cursor-agent login` or `CURSOR_API_KEY`. Models come from `cursor-agent --list-models`, read in the background with eight seconds to answer: `models()` answers at once with what the CLI has listed so far, and starts a read when none is under way. A list with models in it is kept; while there is none (signed out, or the CLI failed), it is read again at most every half a minute, and its models show from the next load of the skill after it. Effort rides on the model string (`model[effort=high]`). A run's model must be one the CLI listed, or `auto`; before any list has arrived, it must have the shape of a model id. The prompt is an argument, so on Windows with a `.cmd` install a prompt of more than one line is refused. The CLI has no setting-source switch, so a run sees the user's `~/.cursor/skills`. This adapter has not been run against a live account.

Isolation is by convention. The skill copy omits `evals/` and the prompt forbids reading outside the sample directory, but nothing stops an agent that follows an absolute path.

## The assistant

Four providers sit behind one port (`src/infrastructure/ai/`). The model in use is a preference, so every control shows the same one. Each vendor's CLI is the main way in and its API key a supported second: `AI_PROVIDER_IDS` lists the CLI first, which is the order of every model list and of the default when nothing is chosen, and Settings folds the key behind "Use an API key" (`VendorRoutes`).

- **anthropic**: the Anthropic SDK with your key. Replies stream, and a field's shape is enforced with structured outputs. The system prompt, which carries the skill and is the same from one turn to the next, is sent as a text block marked `cache_control: ephemeral`, so a later turn reads it at the cached rate. Requests to Fable 5, Opus 5 and Sonnet 5.5 models opt in to Anthropic's server-side fallback, so a request a safety classifier declines is retried on the model Anthropic recommends. A reply may run to 64,000 tokens, or to the model's own limit as the Models API lists it (`max_tokens`) when that is lower.
- **claude-code**: `claude -p` with no tools, settings or skills, on the plan the CLI is signed in to. The shape goes in as `--json-schema`. The brief goes in as `--system-prompt` while it is under 24 KB; a longer one, which Linux's limit on one argument or Windows's on a command line would refuse, leads the prompt on stdin in a `<system>` block, and the argument is one line saying so (`placeBrief`). A command line the system still refuses as too long is reported as a conversation too long to send. The flags every headless `claude` run shares, and the sum of its token counts, are in `src/infrastructure/claude-cli.ts`; a line of a CLI's output that is not a JSON object is never read as an event (`jsonLine`). On Windows the brief always leads the prompt, since a command line takes no line break. One exception: a chat message that starts with `/name` is a command. That run loads the user's settings (`--setting-sources user`, so the user's hooks run too) and keeps slash commands on, the message goes in as the whole prompt so the CLI expands the skill as a terminal would, and the earlier turns go into the system prompt as context, which stays an argument whatever its size. On Windows that argument cannot reach an npm install of the CLI, a `.cmd` script that cmd.exe starts, so there a command is refused before anything runs with a line saying it needs the native install and linking the install guide (`commandProblem`). Tools stay off, so a skill that needs one cannot use it. Each CLI adapter asks its CLI how it is signed in: `claude auth status --json` and `codex login status`. A signed-in answer stands for half a minute (`keptAccount`), so a request does not wait on those two runs; `aiProviderInfo({ fresh: true })` asks again, and an answer of signed out is never kept. That is all the app does to a login. It runs the CLI as its maker publishes it, on whatever account the person signed it in to, with the environment an agent gets (above). It never installs a CLI, never runs `claude auth login`, `claude setup-token` or `codex login`, and never reads a token, a credentials file or the keychain entry a CLI keeps. A CLI that says it is signed out offers no models, and Settings shows the maker's own command (`signInCommand`, and `installCommand` for a CLI that is missing) with **Copy command** and **Check again**. The person runs it in their own terminal, and the row follows when the window gets the focus back. This is the line Anthropic draws: a person may sign in to the unmodified Claude Code with their own account, and a product may not offer Claude.ai login itself, handle its credentials, or use the Claude Code or Anthropic names in a feature name or a logo ([legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)). So the app says in plain text that it runs Claude Code, and no control here is named "Sign in with Claude" or carries a vendor's mark. The status also says what pays (`CliAccount.billing`): a plan, or an API key the CLI found in its environment, which `claude -p` uses ahead of any plan. Settings shows which, so a key is never taken for a plan. A CLI too old to answer counts as signed in.
- **openai**: the OpenAI SDK (Responses API) with your key, with a strict JSON schema for the shape.
- **codex**: `codex exec --json` in a read-only sandbox, on the plan the CLI is signed in to. It reports a reply whole, not word by word.

A reply a provider billed and then refused, because the model declined or the reply ran past its length, is thrown as a `ProviderError` (`src/infrastructure/ai/types.ts`) carrying the `usage` and `model` the reply would have had, so the application records what was spent all the same.

Only `claude-code` has been run against a live account. A command with pictures attached has not been run live.

The side panel's slash menu lists the panel's own commands first (`src/renderer/commands.ts`: clear, settings and guide, run in the page and never sent) and then the skills Claude Code can invoke (`src/domain/commands.ts`, `src/infrastructure/ai/commands.ts`), through `ai.commands`. Only the CLI knows the whole list, with every plugin and every override, and it prints the list in the `init` event of a run before the model is asked. The lister starts such a run on the smallest model with one turn at most (`--model haiku --max-turns 1`) and ends it as soon as that event arrives, so a request to the model is at most cut off as it starts, then reads each skill's description from its file (`~/.claude/skills`, `~/.claude/commands`, or the plugin's folder, under `CLAUDE_CONFIG_DIR` when set). The list is kept in memory for five minutes, and on disk in `~/.skill-studio/claude-commands.json` with the modification times of the folders it was read from (the user's `skills`, `commands`, `plugins` and `settings.json`, and each plugin's folder with its `skills` and `commands` folders), so a backend that starts again uses it until one of those changes. The other providers offer no commands, and the menu does not open on them.

### Changes from the side panel

The side panel's assistant can propose changes to the open skill: a whole file (SKILL.md or one under `references/`), a case to add or replace, and a version to save. The model writes each one as a block fenced with four tildes, so a code fence inside a SKILL.md cannot end it early; a file block closes at the last line of four tildes before the next block or the end of the reply, so a four-tilde fence inside the file is kept too. `src/domain/changes.ts` holds the format: the brief that teaches it (`CHANGES_GUIDE`, part of `chatSystem`) and the parser that reads it (`replyParts`). The panel (`src/renderer/components/Change.tsx`) shows each block as a diff, a case or a version, with one button; how a row stands against the skill, what it says and whether applying it would lose unsaved work, is worked out in `src/renderer/changes.ts`, which is tested.

The assistant reads the skill as the writer has it, not as saved. `chat.send` carries the screen and what is open on it (the Editor's file, the case on Cases: `openAt` in `src/renderer/route.ts`, the same reading those screens use), and the backend lays the skill's stored drafts over its saved files and cases (`workingSkill` in `src/domain/assist.ts`). The drafts on disk are the one copy of unsaved work: the panel stores any still waiting before it sends (`Drafts.flush`), so a keystroke made just before is read. The message being typed is kept in `src/renderer/ai.ts` (`useChatDraft`, and `useImproveDraft` for an improve conversation), so closing the panel or swapping one conversation for the other does not lose it. A reply still being written when the page loads is followed to its end, which in a browser is the only way its end arrives. SKILL.md is read whole. The reference files and the cases share one budget of `CONTEXT_BUDGET` characters: the open file first, then the other references in full while it lasts, then each case in full; a case past the budget is named by its title alone, with a line saying how many were left out. The conversation itself goes back to the model as the newest messages that fit `CHAT_WINDOW` messages and `CHAT_WINDOW_CHARS` characters (`chatWindowOf` in `src/domain/ai.ts`), starting at one from the user. A file change shows against the writer's unsaved text when there is some.

Nothing is written until the writer clicks. The button calls the operations the Skill and Cases screens call (`skill.saveFile`, `skill.saveCase`), and `skill.saveVersion` for a version, so the backend checks the path, the id and the file's text on disk as it does for them, and the status line offers Undo. A file change shows against the shell's copy of the saved files (`ctx.files`), and applying one updates that copy with the write. A reply is marked with the path of the skill it was written about (`ChatMessage.skill`), and its changes are offered only while that skill is open. Whether a change is applied is read from the skill as it stands, never stored.

Each text area is one kind of field (`src/domain/assist.ts`). A kind states the shape its text has, built from the same rule guidance the editor shows. The reply is one JSON object holding that text, fitted to the field before it is shown.

### Improving a selected rule

Selecting four or more words in SKILL.md opens a popout with three actions. Code owns each workflow; a generative model only writes prose.

1. `src/domain/lint.ts` checks each top-level bullet in the selection by word lists and counts: a hedge word with no number or absolute to anchor it, an outcome adjective or a definition in the rule's first sentence, a missing reason, nested bullets, piled conditions, words per rule, and the file's size band. Prose, steps and code are not rules and get no findings; a bare rule with no hedge and no number is left to Jev. Free and instant.
2. `src/judges/rule/index.ts` asks Jev one request over the rule and two lines either side: a yes/no per principle (`RULE_GUIDE`) and a complexity score. `src/domain/improve.ts` turns the probabilities into findings (holds above 0.7, drifts below 0.3, a maybe between). Without a TypeSafe key only step 1 runs.
3. Only then a model is asked, with the findings as its brief:
   - **Auto refine** (`ai.refine`) asks for one revision when anything drifts, and for nothing when the rule complies.
   - **Suggest changes** (`ai.rewrites`) asks for three rewrites in one reply, then has Jev check each kept the selection's facts and that the best practice one now holds every principle. The finished run's text is the `RewritesResult` as JSON.
   - **Help me improve** (`improve.*`) is a conversation in the side panel. The questions live in `IMPROVE_STEPS`, in a fixed order; the plan skips those the judge already cleared. After each reply Jev says whether the question was answered, and code moves on or asks once more. The draft is the last fenced block of the model's reply, and Jev's reading of it is the checklist under it. One button puts it where the selection was, through the editor's registered replacer (`src/renderer/replace.ts`). A rule picked while the last one is still being read takes its place: the earlier start drops Jev's reading, stops any reply it began, and answers with the new conversation, so only the last pick is paid for.

The run kinds `refine`, `rewrites` and `improve` sit beside `assist` and `chat` in `src/domain/ai.ts`.
